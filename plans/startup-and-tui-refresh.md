# Pi startup audit and pi-jar TUI refresh

## Context

Improve `pit`/`pi` startup, centralize pi-jar's visual controls in a clickable welcome-linked pane, remove the unexplained footer `jar` prefix, display live colorized model effort, refine the fire/π welcome, and make past chat easier to scan. Evaluate three adjacent projects without adding conflicting UI extensions. This plan proposes implementation; **no code or user configuration changes occur in planning**.

`pit` is an interactive `~/.zshrc` alias for `PI_TEAM_MATE_COORDINATOR=1 pi`; `pi` is an fnm Node shim. `~/.pi/agent/settings.json` lists 18 packages, including pi-jar, pi-subagents, pi-mono-web-search and another footer owner (`pi-mono-status-line`); 16 skill definitions are discoverable under inspected user/package locations. Pi scans skill metadata at launch and loads full instructions on demand. The shell initializes Java, gcloud, jenv and fnm; its warm/cold costs differ.

**Preliminary, read-only CLI baseline** (`PI_OFFLINE=1`, warm runs, milliseconds): `pi --help` ~1170; `--no-extensions --help` ~165–183; `--no-skills --help` ~1142–1171; pi-jar alone ~182–196. Individually loaded package help commands: pi-mono-web-search ~563, pi-subagents ~583, pi-advisor-flow ~281, pi-mcp-adapter ~268, team-mode ~258. These are non-additive, do **not** measure true interactive readiness, and do not prove which package to disable. One observed first interactive zsh run was ~5200 ms versus subsequent ~360 ms; that one-off is **not a reproducible cold baseline**, and isolated warm Java/jenv/fnm/gcloud timings are far smaller. Label future cold measurements by the reproducible trigger (e.g. fresh login) or report only warm runs and a separately labeled first-run observation; never clear OS caches or require `sudo` to create a cold case. Pi-jar's `session_start` calls two synchronous Git commands (`extensions/index.ts`, each capped at 800 ms); local warm combined timing was ~150–220 ms. In-repo startup savings may be tenths of a second; larger package/shell wins require separate approval. Its footer/welcome timers must also be cleaned up when inactive. Session initialization additionally replays to-dos and costs; measure before optimizing.

Pi's public TUI mouse routing works in **fullscreen** mode only; regular mode leaves the mouse to terminal scrollback/selection. The public custom-message and custom-entry renderers cannot re-layout arbitrary past native messages, so the requested GitHub-inspired chat layout will be a **separate read-only history view**, not a misleading claim that Pi's main transcript was replaced. User chose opt-in fullscreen (no global config edits), persistent visual preferences only, a conversation timeline, and restrained pixel artwork.

## Approach

1. **Audit, then optimize startup.** Use an ephemeral in-memory PTY harness (Python `pty` or an already available Node PTY) to time spawn-to-first visible `pi-jar` welcome/editor marker (or Pi's native editor marker in the extension-free control), then **send an unsubmitted unique sentinel and time its echo** to measure actual input readiness; terminate without model calls. Confirm marker strings in the initial pilot, then collect ≥5 matched **warm** samples and only report cold samples if a repeatable trigger such as a fresh login exists. Compare direct `pi`, `zsh -ic 'pit --offline --no-session'`, `PI_TEAM_MATE_COORDINATOR=1` and no-extension/no-skill controls, noting coordinator-specific hooks. Separate shell/import/session-start/network costs; report median/range, not sums of per-package times. Move pi-jar's synchronous welcome Git probes off the critical path: reuse `footerData.getGitBranch()` if ready; resolve dirty state once with async `execFile`+timeout/cancellation, or omit it if not useful. No subprocess in `render()`, no idle repaint. Resolve duplicate footer ownership *before* footer changes: `pi-mono-status-line` registers one first; verify effective precedence/restoration. If pi-jar owns the footer, proceed; if another extension wins, either use a supported published segment (if available) or present an opt-in user-level de-duplication proposal for separate approval before claiming the footer feature works. Profile cold-shell stages before proposing lazy Java/gcloud/jenv/fnm setup. **Only recommend** changes to `~/.zshrc` or `~/.pi/agent/settings.json` for separate approval; do not disable existing tools.
2. **One settings pane.** Add `/jar settings` and use bare `/jar` to open it in interactive mode (keep `/jar status` and existing commands). Show sections for accent/theme, motion, UI/composer and individual footer fields; keep quota requests explicit, off by default and session-only. Use a width-aware `ctx.ui.custom()` pane with themed focus/help, ↑↓/Tab/Space/Enter/Esc controls and fullscreen `handleMouse`/`MouseRegion` hit targets. Show a clearly framed `[ Settings ↗ ]` action in the welcome; clicking opens the pane, and `/jar settings` provides the regular-mode path without a colliding global shortcut. Launch with `pi --tui-mode fullscreen` or `pit --tui-mode fullscreen` for clicks. Verify that mouse dispatch reaches a welcome *widget* in both installed API versions; if not, use a supported welcome overlay (and keep the `/jar settings` keyboard fallback). Existing `/jar` parsing has no `settings` branch, so the new subcommand does not collide. Create versioned, validated, atomically saved pi-jar visual preferences under `getAgentDir()`, import existing `pi-jar-footer.json` choices on first load, then leave the legacy file read-only (downgrades retain old choices); do not overwrite malformed legacy data. Document that edits made later with a downgraded version will not sync back into the new file without an explicit re-import. Do not change Pi's model, effort, terminal mode, native editor ownership or OAuth consent implicitly.
3. **Footer effort.** `jar` is branding, not a mode; remove the literal prefix but preserve the `DEMO` badge. Read effort at render time from `pi.getThinkingLevel()` (not the default setting), and repaint on public `thinking_level_select` and `model_select` events (both in 0.85.1). Render a textual off/minimal/low/medium/high/xhigh/max chip using existing `thinkingOff`…`thinkingMax` colors, with narrow-width abbreviation. A non-reasoning model displays dim `off`; gracefully fall back if a palette/API value is absent. Preserve context, failure/active-role priority, field visibility and cell-width bounds.
4. **Welcome design.** Widen the art column and add balanced side padding around a recognizable pixel π, with smoother edges and a fixed-position status card. Replace four jumpy smoke/flame frames with ~6–8 coherent, fixed-width shaded amber/terracotta fire frames and subtle rising smoke; keep a deliberate fire/π gap and static or barely pulsing π so two large regions do not compete. Respect the motion toggle, low-color/font fallback, reduced repaint budget, tiny terminals and dismissal/shutdown cleanup. Avoid font-dependent Braille/emoji or an intense neon glow.
5. **Chat timeline.** Add `/jar history` as a separate read-only view backed by `ctx.sessionManager.getBranch()`: user/assistant turn cards, author/sequence, timestamp only when present, compact prose/Markdown/code excerpts, expandable tool details, keyboard scrolling/search/navigation and fullscreen pointer support. Sanitize untrusted session-derived content; cap per-entry work, lines and viewport for long sessions; reflect active branch on reopening. Keep Pi's main transcript and stored messages unchanged. Consider minor theme color alignment for native messages, but do not patch private transcript classes.
6. **Borrow patterns, not dependencies.** From [pi-animations](https://github.com/arpagon/pi-animations): phase-aware/static motion, **not** its private collapsed-thinking monkey patch. From [cli-spinners](https://github.com/sindresorhus/cli-spinners): matching frame sets and frame intervals, **not** its runtime package. From [pi-beautiful-tui](https://github.com/YoungJurry/pi-beautiful-tui): semantic effort colors, cohesive settings hierarchy and no-subprocess startup discipline, **not** another extension replacing pi-jar's footer/editor.

Report timing distributions and regressions, not a single marketing figure.

## Decisions and limits

- Global shell/Pi configuration is **diagnosed and proposed**, not edited without separate approval.
- Clicks require opt-in fullscreen; regular mode retains keyboard use and terminal selection.
- Persist visual choices (accent, footer, animation, composer); quota stays session-only. Effort is read-only Pi-owned status.
- History is a separate conversation timeline because native historical chat layout cannot be changed through supported renderer hooks. No unsupported Pi core patch.
- Visual direction: refined pixel π and subtly animated amber/terracotta flame.
